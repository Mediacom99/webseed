# Frontend Architecture

Internal dashboard for operating the webseed pipeline. Built with React + Vite as a single-page application.

## Tech Stack

| Layer | Choice | Notes |
|-------|--------|-------|
| Framework | React 19 + Vite | SPA, no SSR needed for internal dashboard |
| Language | TypeScript (strict mode) | Matches backend's Pyright strict |
| Components | shadcn/ui (Radix + Tailwind) | Copy-paste components, full ownership |
| Pipeline visualization | React Flow (xyflow) | Node-based pipeline graph with animated edges |
| Animation | Framer Motion | Pipeline step transitions, progress animations |
| Styling | Tailwind CSS | Comes with shadcn/ui |
| Icons | Lucide | Default in shadcn/ui |
| Routing | react-router-dom | Client-side routing |
| API client | Orval (auto-generated) | Generates typed hooks from `openapi.json` |
| Server state | TanStack Query | Caching, refetch, mutations, devtools |
| Client state | Zustand | WebSocket connection, active job state |
| Forms | react-hook-form + Zod | Zod schemas auto-generated by Orval |
| E2E testing | Playwright | Critical user flows |
| Unit testing | Vitest + Testing Library | Store logic, utilities |

## App Type

- **Internal dashboard** — single user/team operating the webseed pipeline
- **No public pages**, no SEO, no multi-tenancy
- **Hero page**: Pipeline Runner — start jobs, monitor progress in real-time
- **Workflow**: Open app → check stats/status → decide what to run → go to Pipeline Runner

## Auth

The backend uses a single API key via `X-API-Key` header. WebSocket uses `?api_key=` query param.

- API key entered on login page, stored in **localStorage**
- Attached to every request via Orval's custom fetch instance
- Route protection: `AuthGuard` layout wrapper — redirects to `/login` if no key
- No roles, no sessions, no token refresh

## Pages & Routes

| Page | Route | Purpose | API Endpoints |
|------|-------|---------|---------------|
| Login | `/login` | API key input + validation | Test call to any endpoint |
| Dashboard | `/` | Stats overview, recent activity, active jobs, quick actions | `GET /businesses/stats`, `WS /ws` |
| Pipeline Runner | `/pipeline` | React Flow pipeline viz, start jobs, business progress table, live event feed | `POST /pipeline/*`, `WS /ws` |
| Businesses | `/businesses` | Filterable/sortable data table, bulk actions, CSV export | `GET /businesses`, `GET /businesses/stats` |
| Business Detail | `/businesses/:placeId` | Full business data, status management, generated site preview | `GET /businesses/{place_id}`, `PATCH status`, `POST blacklist` |
| Settings | `/settings` | Prompt templates editor + config values (tabbed) | `GET /settings`, `PUT /settings/{key}` |

## Navigation

Collapsible left **sidebar** with:
- Logo/app name at top
- Nav items: Dashboard, Pipeline, Businesses, Settings
- Active job indicator badge on Pipeline nav item when a job is running
- Collapses to icon-only on smaller screens

## Pipeline Runner Design

The hero page uses **React Flow** for the pipeline visualization:

- **6 nodes**: Search → Enrich → Generate → Test → Deploy → Email
- Custom nodes showing step status (queued, running, done, error) with animated transitions
- Animated edges showing flow between steps
- Below the flow: **Business progress table** showing each business's status within the current job
- Below the table: **Live activity feed** streaming WebSocket events chronologically

### Starting a Job

The Pipeline Runner page includes forms for:
- **Search**: location, query, types, limit, min_score, grid_size
- **Run pipeline**: select businesses (from search results or business list), choose model, toggle playwright testing
- Individual step triggers: enrich, generate, test, deploy, email (for selected businesses)

## Real-Time Architecture

Single persistent **WebSocket** connection managed in Zustand:

```
WebSocket (/ws?api_key=...) → Zustand store → subscribers
                                    ↓
                              TanStack Query cache invalidation
```

- **Connection lifecycle**: Connect on login, reconnect with exponential backoff on disconnect
- **Event distribution**: Components subscribe to specific event types/job_ids via Zustand selectors
- **Cache invalidation**: `step_done` events trigger TanStack Query refetch for the affected business
- **Cross-page updates**:
  - Pipeline Runner: updates React Flow nodes, progress table, activity feed
  - Dashboard: updates active job count, recent activity
  - Sidebar: shows running job badge

### WebSocket Event Types

```typescript
interface PipelineEvent {
  event_type: 'step_start' | 'step_done' | 'step_error' | 'progress' | 'cost' | 'job_complete';
  job_id: string;
  step: 'search' | 'enrich' | 'generate' | 'test' | 'deploy' | 'email';
  place_id?: string;
  message: string;
  data?: Record<string, unknown>;
  timestamp: string;
}
```

## Data Fetching

### Orval Code Generation

Orval reads `openapi.json` and generates:
- Typed **TanStack Query hooks** for every endpoint (e.g., `useListBusinesses()`, `useGetStats()`)
- **Zod schemas** for request/response validation
- **TypeScript types** for all API models

Config in `orval.config.ts`:
- Input: `../openapi.json`
- Output: `src/api/`
- Client: custom fetch instance (attaches `X-API-Key` header from localStorage)

Regenerate after backend API changes: `npm run generate-api`

### TanStack Query Patterns

- **Business list**: `useListBusinesses({ status })` with filter params
- **Stats**: `useGetStats()` with short stale time (refetch frequently)
- **Settings**: `useListSettings({ prefix })` — longer stale time
- **Mutations**: `usePipelineSearch()`, `usePipelineRun()`, etc. — invalidate relevant queries on success
- **Optimistic updates**: For status changes and blacklist toggles

## Forms

### Libraries
- **react-hook-form**: Uncontrolled forms with shadcn/ui's `<Form>` component
- **Zod**: Validation schemas (auto-generated by Orval where possible, manual for UI-only forms)

### Key Forms
- **Search form**: location (text), query (text), types (multi-select), limit (number), min_score (slider/number), grid_size (number)
- **Run pipeline form**: business selection (checkbox table), model (select), test_model (select), max_fix_iterations (number), no_email (toggle), playwright (toggle)
- **Settings editor**: key (read-only), value (textarea for prompts, text for config), description (text)

### Error Handling
- Zod validates client-side before submission
- API 422 errors (FastAPI `ValidationError`) mapped to form field errors via `loc` array
- Toast notifications for non-field errors

### Naming Conventions
- **Components**: PascalCase files (`BusinessTable.tsx`)
- **Utilities/stores/hooks**: camelCase files (`websocket.ts`, `useWebSocketEvents.ts`)
- **No barrel exports**: Import directly from file, not via `index.ts` re-exports
- **Pages are thin**: Compose feature components, minimal logic in page files

## Local Development

### Prerequisites
- Node.js 20+
- Backend running on `localhost:8000` (`python -m webseed`)
- PostgreSQL running (`docker compose up -d`)

### Setup
```bash
cd frontend
npm install
npm run generate-api    # Orval generates API client from openapi.json
npm run dev             # Vite dev server on localhost:5173
```

### Vite Dev Proxy

`vite.config.ts` proxies API and WebSocket requests to the backend:

```typescript
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8000',
        rewrite: (path) => path.replace(/^\/api/, ''),
      },
      '/ws': {
        target: 'ws://localhost:8000',
        ws: true,
      },
    },
  },
});
```

Note: The backend doesn't have an `/api` prefix — the proxy rewrites `/api/businesses` → `/businesses`. The frontend always calls `/api/*`, which maps cleanly for both dev proxy and future production reverse proxy.

### Environment Variables

| Variable | Default | Description |
|----------|---------|-------------|
| `VITE_API_BASE_URL` | `/api` | API base URL (proxy handles in dev) |
| `VITE_WS_URL` | `/ws` | WebSocket URL (proxy handles in dev) |

## Testing

### Unit Tests (Vitest)
- WebSocket store logic (event parsing, subscription filtering)
- Auth store (localStorage get/set/clear)
- Utility functions
- Located alongside source files or in `__tests__/` directories

### E2E Tests (Playwright)
- Login flow: enter API key → redirected to dashboard
- Pipeline flow: search → start pipeline → monitor progress
- Business management: filter table → view detail → change status
- Settings: edit prompt → save → verify
